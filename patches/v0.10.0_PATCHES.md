# Function-KRO Adaptations for KRO v0.10.0

This document is the **upgrade guide** for re-applying function-kro's adaptations when upgrading to a new upstream KRO version. It is designed to be used by an agent following `UPGRADE_PROCESS.md` Phase 3.

For each adaptation, this document provides:
1. **What to look for** in the new upstream code
2. **What to do** (remove, replace, or modify)
3. **The function-kro code**, so you can reconstruct it even if upstream changed significantly
4. **Conditional guidance** for when upstream may have changed

Based on a full audit using `./scripts/diff-upstream-kro.sh -r v0.10.0`.

**The diff script skips `*_test.go` files.** We vendor no upstream tests. Upstream's executor tests drive a real or fake API server through the code paths our adaptations bypass, so they don't apply.

## Quick Reference

### What We Vendor

We vendor one upstream package: `pkg/graphengine/executor` into `kro/graphengine/executor/`. Everything else we use from kro (`api/v1alpha1`, `pkg/graphengine/rgdadapter`, `pkg/graphengine/compiler`, `pkg/graphengine/runtime`, `pkg/cel`, `pkg/graph`, `pkg/metadata`, `pkg/features`, and the executor's own imports `pkg/applyset` and `pkg/graphengine/watchrouter`) is imported unmodified as the Go module `github.com/kubernetes-sigs/kro`, at the version pinned in `go.mod`.

The "Vendoring Rules" section of `UPGRADE_PROCESS.md` has the rules for what we vendor and where code that repeats upstream logic may live. This document lists what those rules produce for v0.10.0.

## Changes from v0.9.0 Adaptations

### New upstream architecture in v0.10.0

Upstream PR https://github.com/kubernetes-sigs/kro/pull/1355 (KREP-024, "RGD on Graph", design doc https://github.com/kubernetes-sigs/kro/blob/v0.10.0/docs/design/proposals/graph.md) deleted `pkg/runtime`, which v0.9.0 vendored, and moved instance reconciliation into `pkg/graphengine`:

- `rgdadapter` translates an RGD into a `Graph`
- `compiler` compiles the `Graph` into a `Program`
- `runtime` evaluates a `Program` one node at a time
- `executor` walks the nodes in order and applies them to the API server

The compiler now takes its schema resolver and REST mapper as injected dependencies (`compiler.NewCompilerWithDependencies`), and options such as `compiler.WithNodeSchemaOverride` and `runtime.WithSeedScope` let a caller type and seed the `schema` node itself. Those extension points close most of the gaps our v0.9.0 adaptations bridged, so we now import the graph, CEL, compiler and runtime layers unmodified. We vendor only the executor, the one layer that still assumes an API server. The RGD adapter's runtime builder types the `schema` node from a SimpleSchema, but it compiles through a `Compiler` interface we pass in, so we wrap the compiler to type the node from the XR's schema instead (`engine.go` `newXRSchemaCompiler`).

### Fate of each v0.9.0 adaptation

| v0.9.0 adaptation | Outcome | Where it went |
|-------------------|---------|---------------|
| 1. Builder constructor accepts a resolver | Gone | `compiler.NewCompilerWithDependencies` takes our resolver (`fn.go`) |
| 2. `NewResourceGraphDefinition` takes the XR schema | Gone | We no longer call `graph.Builder`. `newXRSchemaCompiler` (`engine.go`) gives the compiler the XR schema through `compiler.WithNodeSchemaOverride` |
| 3. `buildInstanceNodeFromSchema` | Moved | Same as 2. `instanceSchemaForCEL` in `engine.go` replaces upstream's `graph.InstanceSchemaForCEL` |
| 4. `getSchemaWithoutStatus` takes a `*spec.Schema` | Moved | Same as 3 |
| 5. Remove the REST mapper from `buildRGResource` | Gone | The compiler takes an injected REST mapper. We pass one that infers scope (`engine.go` `restMapperFor`) |
| 6. Remove `GVR` and `Namespaced` from `NodeMeta` | Gone | Nothing to remove, since the scope comes from our REST mapper |
| 7. Iterator identity simplification | Gone | Lived in `graph.Builder`, which we no longer call |
| 8. Remove namespace normalization | Moved | Namespace defaulting now lives in the executor. Adaptation 3 below keeps it for the runtime's copy of each object and leaves it off what we return to Crossplane |
| 9. Validation changes | Gone | We skip `graph.Builder` validation. The compiler still type checks expressions and catches cycles and invalid or duplicate IDs. What we lose is listed in `patches/UPSTREAM_DIFFERENCES.md` |
| 10. Metadata package | Gone | Imported unmodified |
| 11. Test utility generator | Gone | No vendored tests |
| Files added: schema resolvers | Moved | No longer inside a vendored package, so they live in `internal/schemaresolver/` as ordinary function-kro code |
| `DeepCopySchema` addition to `schema.go` | Gone | A JSON round trip where a copy is needed |

## Adaptation 1: `Crossplane` field on `Simple` (`kro/graphengine/executor/simple.go`)

### What to look for

The `Simple` struct, which holds a `Client client.Client` that every apply, read, watch and delete goes through.

### What to do

Add a `Crossplane *Crossplane` field at the end of the struct. Leave `Client` in place; it stays nil, and keeping it means upstream code that references it still compiles.

**If upstream adds an interface for cluster I/O that `Simple` calls through:** consider implementing it in `crossplane.go` instead, and dropping Adaptations 3 to 6.

### Function-kro code

```go
	OnToleratedRejection func(ToleratedRejection)
	// Crossplane replaces the API server for a composition function: it
	// collects desired state instead of applying it, and answers reads from
	// what Crossplane sent. See crossplane.go.
	Crossplane *Crossplane
}
```

## Adaptation 2: Preserve resources for nodes `Apply` can't process (`kro/graphengine/executor/simple.go`)

### What to look for

In `Simple.Apply`, the soft-error branches that record a node as `Unresolved` and `continue`: waiting on an unready dependency, `includeWhen` data pending, and `Resolve` data pending. Upstream's caller keeps the previous managed resources for unresolved nodes instead of pruning them.

### What to do

Call `s.preserve(ctx, rt, n)` just before `continue` in each of those three branches.

Crossplane deletes any composed resource a function stops returning, so holding back pruning isn't enough for us. `preserve` (in `crossplane.go`) renders the node again and returns it as desired state if Crossplane already created it, or records a hard error if it can't be rendered at all. For an external ref, `preserve` reads it through `applyNodeByKind`, so an existing resource that reads the ref can still be rendered again, and Crossplane keeps fetching it.

`fn.go` turns a hard error from the walk, including one from `preserve`, into a fatal result, except while Crossplane still has to fetch an external ref we asked for. Crossplane won't fetch anything after a fatal result, and it calls the function again once it has fetched the ref.

**If upstream adds a soft branch in `Apply` that marks a node `Unresolved` before it is applied:** add a `preserve` call there too, or Crossplane will delete that node's resources.
**If upstream moves these branches into a helper:** put the call in the helper.

### Function-kro code

```go
			if dep, blocked := firstUnreadyDep(n, ready); blocked {
				result.Unresolved = append(result.Unresolved, n.ID())
				recordSoft(fmt.Errorf("apply %q: waiting for dependency %q: %w", n.ID(), dep, ErrNotReady))
				s.preserve(ctx, rt, n)
				continue
			}
```

The `includeWhen` and `Resolve` branches get the same one-line insertion.

## Adaptation 3: Template nodes become desired state (`kro/graphengine/executor/simple.go`)

### What to look for

In `applyNodeByKind`, the `compiler.NodeKindTemplate` case calls `s.applyTemplate(ctx, rt, w, n, desired)`, which namespace-defaults each object, stamps kro labels, registers a drift watch, reads the live object, and server-side applies it. The case then calls `n.SetObserved(desired, desired)` and `publishScope`, relying on the apply having written the server's response back into `desired`.

### What to do

Replace the `applyTemplate` call with `s.emitTemplate(rt, n, desired)`. Leave the rest of the case, including `SetObserved` and `publishScope`, unchanged. `emitTemplate` follows the same contract: it writes each object's server view (the observed resource, or the rendered one if Crossplane hasn't created it yet) back into `desired`, and returns a soft `ErrNotReady` when a node with `readyWhen` has resources Crossplane hasn't created yet.

Leave `applyTemplate` and everything it calls in the file. They're unreachable, but deleting them would grow our diff.

`emitTemplate` repeats what `applyTemplate` does to each object before applying it, in `buildMappings` and `prepareItem`: it calls `mappingFor` and `defaultNamespace`, and claims the object's identity with a key in the same `apiVersion/kind/namespace/name` format, built by `identityKey` in `crossplane.go`. We can't call `prepareItem` itself, for two reasons. It claims an identity for objects without a name, and since Crossplane generates those names, two unnamed resources of one kind would falsely collide. It also stamps kro's labels and annotations, and we stamp only `kro.run/collection-index`. The diff script can't see this copy, so it's listed under "Upstream Logic Our Additions Repeat" below.

**If upstream changes `buildMappings` or `prepareItem`, or what `applyTemplate` does to an object before applying it** (namespace defaulting, identity claims, labels): decide whether `emitTemplate` and `identityKey` need the same, ignoring anything that exists only for SSA, watches, applysets or pruning.
**If upstream changes the `SetObserved`/`publishScope` contract after the apply:** update `emitTemplate` to match.

### Function-kro code

```go
	case compiler.NodeKindTemplate:
		applied, err := s.emitTemplate(rt, n, desired)
```

## Adaptation 4: The status patch node becomes the desired XR status (`kro/graphengine/executor/simple.go`)

### What to look for

In `applyNodeByKind`, the `compiler.NodeKindPatch` case calls `s.applyPatch(ctx, rt, w, n, desired)`, which server-side applies patch contributions to targets, including the instance's status subresource.

### What to do

Replace the call with `s.capturePatch(n, desired)`. The only patch node an RGD produces is the synthesized status node (`rgdadapter.StatusPatchNodeID`), and `capturePatch` stores its rendered `status` as the desired XR status.

**If `rgdadapter` starts producing other patch nodes from an RGD:** `capturePatch` ignores them silently. Decide how they map to Crossplane desired state.

### Function-kro code

```go
	case compiler.NodeKindPatch:
		contributions, err := s.capturePatch(n, desired)
```

## Adaptation 5: External refs read what Crossplane fetched (`kro/graphengine/executor/simple.go`)

### What to look for

In `applyRef`, the `s.Client.Get(ctx, key, live)` call that reads the referenced object, treating NotFound as not ready.

### What to do

Replace it with `s.Crossplane.Get(n.ID(), key, live)`. `Get` asks Crossplane to fetch the object via a required resource selector and answers from what Crossplane sent, returning NotFound until it has. Everything around the call, including namespace defaulting and the NotFound handling, stays upstream's.

### Function-kro code

```go
	if err := s.Crossplane.Get(n.ID(), key, live); err != nil {
```

## Adaptation 6: External collections read what Crossplane fetched (`kro/graphengine/executor/simple.go`)

### What to look for

In `applyRefCollection`, the `s.Client.List(ctx, list, opts...)` call that lists objects matching the external ref's label selector.

### What to do

Replace it with `s.Crossplane.List(n.ID(), list, opts...)`. `List` asks Crossplane to fetch by the selector's `matchLabels`, since Crossplane can only select by exact label values (https://github.com/crossplane/crossplane/issues/6744), and filters what comes back by the full selector, including `matchExpressions`. It returns an error wrapping `ErrNotReady` until Crossplane has answered, which `applyNodeByKind` treats as soft.

The drift watch registration just above the call is skipped because we pass a nil watcher, so it needs no change.

### Function-kro code

```go
	if err := s.Crossplane.List(n.ID(), list, opts...); err != nil {
```

## Files Added (Not in Upstream)

### `kro/graphengine/executor/crossplane.go`

Upstream doesn't have this file, so copying a new upstream version never overwrites it. It holds everything Crossplane-specific in the vendored package:

| Code | Stands in for | Notes |
|------|---------------|-------|

## Upstream Logic Our Additions Repeat

Our code repeats a few pieces of upstream logic that we can't call directly. The diff script can't see these copies, so on every upgrade, compare each upstream function between the two versions and carry any change into our code.

| Our code | Repeats | Upstream file |
|----------|---------|---------------|
| `Simple.emitTemplate`, `identityKey` (`executor/crossplane.go`) | `buildMappings` (`mappingFor`), and `prepareItem` (`defaultNamespace`, the identity claim and its key format). Leaves out claims for unnamed objects and kro's labels (Adaptation 3) | `pkg/graphengine/executor/simple.go` |
| `Simple.preserve` (`executor/crossplane.go`) | The template path through `Apply` and `applyNodeByKind`: `Resolve`, apply, then `SetObserved` and `publishScope` (Adaptation 2) | `pkg/graphengine/executor/simple.go` |

| `RunFunction`'s forEach dimension check (`fn.go`) | The dimension count check at the top of `validateForEachDimensions`, and its error message, using `--rgd-max-collection-dim-size`. Upstream's runs inside RGD validation, which is unexported | `pkg/graph/validation.go` |

## Upstream Code We Keep but Never Run

These stay in `simple.go` verbatim so our diff stays small. None of them run, because our rerouted call sites never reach them:

- `applyTemplate`, `applyScalarTemplate`, `applyCollectionTemplate`, `applyCollectionItem`, `getLive`, `stampKROMeta`, `applyTemplateObject` and the field-manager conflict helpers (replaced by `emitTemplate`)
- `applyPatch`, `applyPatchOne`, `contributeApply`, `replaceStatus` (replaced by `capturePatch`)
- `Delete` and `Release` (we never call them; Crossplane garbage collects composed resources)
- `applySubgraph` (only the `Graph` kind produces subgraph nodes, never an RGD)

**`Simple.Client` is always nil.** Any upstream call through `s.Client` on a path we do run would panic. `mappingFor` calls `s.Client.RESTMapper()` for a node whose `apiVersion` or `kind` is a CEL expression. `fn.go` rejects such nodes before calling `Apply` (see "Our Code That Depends on Upstream Behavior" below), so that path never runs. On every upgrade, check each `s.Client` reference in functions reachable from `Apply` for `Def`, `Template`, `Ref` and `Patch` nodes.

## Our Code That Depends on Upstream Behavior

None of this code copies upstream code; anything that does is listed under "Upstream Logic Our Additions Repeat". It stands in for something upstream gets from the API server or its controller, so an upstream change can still break its assumptions without touching anything the diff script sees. Check each on every upgrade:

| Our code | Depends on | What to check |
|----------|------------|---------------|
| `engine.go` `restMapperFor` | The REST mapper the compiler and executor query, which upstream backs with the API server | What upstream uses scope for |
| `fn.go` `setAuthorConditions` | The built-in conditions upstream's controller passes to `rgdadapter.ProjectInstanceConditions` (`pkg/controller/instance/controller_graph_engine.go`) | Which built-in condition types exist and what they mean. We approximate them from the walk |
| `engine.go` `newXRSchemaCompiler` | `rgdadapter.BuildRuntimeForInstance` compiles through the `Compiler` we pass and sets its own `WithNodeSchemaOverride` for the `schema` node; the compiler keeps the last override for a node, so ours wins | That both still hold. If upstream lets callers supply the `schema` node's type directly, use that instead |
| `fn.go` rejection of nodes with `DynamicGVK()` | `Simple.mappingFor` | Whether upstream still needs a live REST mapper for a CEL `apiVersion` or `kind` |
| `fn.go` function context (`schema.context`) | `runtime.WithNodeObjectOverride` renders the `schema` node from the object we pass, as is. `rgdadapter.InstanceSchemaNode` keeps only `apiVersion`, `kind`, `metadata`, `spec` and `status`, so without the override the context is dropped | That the override still replaces the `schema` node's payload, and that `BuildRuntimeForInstance` still passes our runtime options through |

## Schema Resolution Architecture

Function-kro uses capability-based detection in `fn.go` to choose a schema resolution path. This is not in the kro libraries, but it explains why we inject a resolver into the compiler.

### Path 1: Required Schemas (Crossplane v2.2+)
```
HasCapability(REQUIRED_SCHEMAS) -> response.RequireSchema() -> request.GetRequiredSchemas()
    -> structToSpecSchema() -> schemaresolver.SchemaMapResolver -> schemaresolver.NewCombinedResolverFromSchemas()
    -> resolver.SchemaResolver passed to compiler.NewCompilerWithDependencies()
```

### Path 2: CRDs (Fallback for older Crossplane)
```
!HasCapability(REQUIRED_SCHEMAS) -> request CRDs via required_resources
    -> request.GetRequiredResources() -> schemaresolver.NewCRDSchemaResolver()
    -> schemaresolver.NewCombinedResolverFromCRDs() -> resolver.SchemaResolver passed to compiler.NewCompilerWithDependencies()
```

Both paths produce the same `resolver.SchemaResolver` interface that the compiler consumes.

## Known Limitations

`patches/UPSTREAM_DIFFERENCES.md` lists where function-kro behaves differently from upstream kro, including validation we skip.

## Upstream Behavior We Intentionally Don't Need

1. **Server-side apply, field managers, applysets and conflict detection.** Crossplane applies composed resources.
2. **Pruning, `Delete` and `Release`.** Crossplane garbage collects composed resources it no longer receives as desired.
3. **Drift watches.** Crossplane re-runs the function.
4. **kro's identity labels and annotations** (`node-id`, `collection-size`, `node-path`, `apply-order`). Only upstream's watches and pruning read them. We stamp only `collection-index`.
5. **CRD synthesis and revision tracking.** Crossplane manages the XR's CRD, and a function run is stateless.
